## Dojoruとは

AWS資格試験「SAP-C02」対策アプリ「Dojoru」を、AI(Claude Code)と協業しながら個人開発している記録シリーズです。最終回となる今回は、Windowsだけでどうやって Android と iOS の両方をビルド・配信まで持っていったか、という運用の話と、シリーズ全体の振り返りをします。

→ アプリの詳細はこちら: <https://jk2014jp.github.io/dojoru-public/>
[![Google Playで手に入れよう](/images/google-play-badge-ja.png)](https://play.google.com/store/apps/details?id=com.dojoru.app)

## EAS Buildという選択

第4回で書いた通り、Dojoruが Expo(React Native)を採用した最大の理由は「Windows環境からiOSビルドをしたい」でした。これを実現するのが **EAS Build**(Expoが提供するクラウドビルドサービス)です。手元のPCでコンパイルするのではなく、コマンド一つでクラウド上のビルドサーバー(iOSの場合はクラウド上のMac環境)にソースを送り、ビルド済みのアプリファイルを受け取れます。

Android・iOSそれぞれ、次のようなコマンドで本番ビルドを実行しました。

```bash
eas build --platform android --profile production
eas build --platform ios --profile production
```

ちなみに、EAS Buildには無料枠があり(Android・iOSそれぞれ月15回まで、優先度の低いキューでビルドタイムアウトは45分)、Dojoruのこれまでの実ビルド回数はAndroidが6回前後・iOSが4回前後にとどまったため、EAS Build自体の利用料は今のところ一度も発生していません。これは偶然ではなく、第4回で触れた、Androidをローカルビルドで作り込んでから初めてEAS Buildに進む、という運用を徹底していたからこそ実現できた回数です。個人開発でまず試してみる分には、コスト面のハードルはかなり低いと感じました。

## Androidはスムーズ、iOSは最初だけ一手間

Android版は、EAS側で管理された署名鍵を使い、比較的スムーズにビルドできました。パッケージ名は開発初期の仮の名前から、公開後は変更できない正式な名前へ、リリース直前に確定させています。

iOS版は、最初の1回だけ壁がありました。

1. Apple Developer Programへの支払い直後、「有効なチームが紐づいていない」というエラーでビルドが失敗(これは支払い後のアカウント有効化を待つ、よくある遅延でした)
2. アカウント有効化後、**証明書やプロビジョニングプロファイルの新規作成は、非対話モードのコマンドでは実行できない**という制約に当たりました。これはApple IDでの認証が必要なため、開発者本人が対話的にコマンドを実行する必要があります

一度、対話モードで証明書一式を作成してしまえば、その情報はEAS側のクラウドに保存されます。**2回目以降のビルドや、TestFlightへの提出は、AI(Claude Code)が非対話モードのコマンドだけで完結できるようになりました**。「最初の鍵開けだけ人間が行い、以降の運用はAIに任せる」という役割分担がきれいに決まった瞬間でした。

余談ですが、この最初に成功したiOSビルドは、実測で**約5分**で完了しました。「クラウド上のMacでビルドする」と聞いて身構えていましたが、体感としては想像より速く、拍子抜けするくらいでした。

## AIの外での最大の壁: Androidクローズドテストのテスター集め

ここまでAIとの協業の話を中心に書いてきましたが、リリース作業の中で一番苦労したのは、実はAIが手伝えない部分でした。Google Playでは、個人開発者が本番リリースするには、事前に「クローズドテスト」で**12名以上のテスターに、最低14日間連続でオプトインし続けてもらう**必要があります(以前は20名でしたが、2024年12月の要件緩和で12名になりました)。

最初は知人に頼めば何とかなるだろうと軽く考えていました。ところが、いざ声をかけてみると、日本ではiPhoneのシェアがとにかく強く、身の回りでAndroid端末を持っている知人がなかなか見つからない、という壁にぶつかりました。

そこで方針を変え、X(旧Twitter)で同じような境遇の個人開発者を探し、片っ端から「テスターをお願いできませんか」と声をかけていきました。同じように個人でAndroidアプリを作っている人は、当然この12名の壁の大変さを分かっているので、お願いすれば互いにテスターとして協力し合う、という関係が自然とできていきました。

2026年7月30日にクローズドテストを開始し、2026年8月3日には登録テスターが12名を突破しました。ただし、これで即リリースできるわけではありません。その12名以上に、最低14日間連続でオプトインし続けてもらって初めて、本番トラックへの申請条件が揃います。途中で誰かがオプトインを外すとカウントがリセットされてしまう仕組みのため、テストが始まってからも気は抜けませんでした。技術的な壁はAIと一緒に乗り越えられましたが、この「人を集める」壁だけは、最後まで自分の足で稼ぐしかありませんでした。

## リリースノートもAIと一緒に作った

Android・iOSともにビルドが揃ったら、Play Console・TestFlightにそれぞれ提出しますが、その際に必要なのが「リリースノート」(更新内容の説明文)です。今回は、直近のコミット履歴を一つずつ振り返り、**ユーザー向けの言葉に翻訳する**という作業をAIと一緒に行いました。「dismissAllへの変更」のような技術的な話は、「戻る操作を繰り返した際にアプリが誤って終了することがある不具合を修正しました」というユーザー向けの一文に変換する、という具合です。

この翻訳作業が思いのほか早く終わったのは、コミット履歴だけを頼りに一から書き起こしたからではありません。各コミットはタスク管理表・課題管理表の該当エントリに紐づいていて、そこには「何が起きて、何をどう直したか」がすでに日本語で記録済みでした。この記事で何度も出てきた台帳が、ここでも下書きの役目を果たしてくれた形です。

## シリーズを振り返って: 学んだこと

全9回、駆け足でしたが、最後にAIとの協業から得た学びをまとめます。

1. **モデルの使い分け**: 戦略判断は上位モデルで、定型的な多ファイル変更は軽量モデルに任せつつ、必ず上位モデルが差分とテストを検証する
2. **モックファースト**: 見た目に関わる変更は、まず簡易なモックで試してから実装する
3. **実機検証の徹底**: エミュレータでは気づけない不具合は、都度実機で確認する
4. **多層チェックがコンテンツ品質を救う**: 作った本人のセルフチェックだけに頼らず、独立した第三者(別ロール)のチェックを挟む
5. **台帳(ID体系)がAIの長期記憶を代替する**: 長期プロジェクトでも、REQ/TASK/ISSUE番号さえ追えれば経緯を辿れる設計にしておく

「AIに仮想的な組織を持たせて、個人開発を1人でやり切る」という試みは、正直まだ発展途上だと思っています。それでも、思いつきで進めるよりも遥かに一貫性のある開発ができた実感があります。この記録が、同じようにAIと個人開発に取り組む方の参考になれば嬉しいです。
