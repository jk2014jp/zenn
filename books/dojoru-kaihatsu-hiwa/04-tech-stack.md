## Dojoruとは

AWS資格試験「SAP-C02」対策アプリ「Dojoru」を、AI(Claude Code)と協業しながら個人開発している記録シリーズです。今回は、プロジェクト開始からわずか2日で技術スタックを丸ごと乗り換えた話をします。

→ アプリの詳細はこちら: <https://jk2014jp.github.io/dojoru-public/>

## 最初はFlutterで始めていた

Dojoruは当初、Flutter + Riverpod(状態管理) + Drift(SQLiteラッパー) + fl_chart(グラフ描画)という構成で計画していました。セットアップ手順書も、TypeScriptならぬDartのスターターコードも、一通り準備が済んでいた状態です。

Flutterを選んだ理由は主に2つありました。1つは、1つのコードベースでAndroid・iOSの両方を作れる**マルチプラットフォーム対応**です。もう1つは、単純に**Dartという言語を一度使ってみたかった**という、技術的な好奇心でした。

ところが、プロジェクト開始2日目にして、この構成を全部やり直すことになりました。第1回の最後で少し触れた「Expo」という選択肢を、ここで本格的に検討することになります。

## 理由は「Windowsだけで iOS を作りたい」

開発環境はWindows 10です。Flutterで開発を進めても、**iOS版をビルドするには基本的にMacが必要**という制約にぶつかります。個人開発で、わざわざこのためだけにMacを用意するのは現実的ではありません。

Macの購入も一応検討しました。ただタイミングが悪く、ちょうどMacが値上げされた直後で、予算を抑えられるMacBook Neoでは開発に必要なスペックとしては力不足でした。さらに、ちょうどWindows 10のサポート期限が切れるタイミングでもあり、新しいWindowsパソコンを注文した直後だったことも重なりました。結局Macの購入は見送り、他に解決策がないか模索することにしました。

そこで技術スタックを次の構成に変更しました。

- **Expo(React Native + TypeScript)**
- **expo-sqlite**(Drizzle ORM経由)
- **EAS Build**(Expoのクラウドビルドサービス)

EAS Buildを使うと、**Windows上で `eas build --platform ios` を実行するだけで、クラウド上のMac環境でiOSアプリがビルドされます**。ローカルにMacがなくても、Android・iOS両方のアプリを作れるわけです。これがExpo移行の一番の決め手でした。

## 「もう一度考え直す」意思決定をどう回したか

Claude Code(PM役)に技術スタック変更の影響分析を依頼し、即日で承認・切り替えという流れになりました。ポイントは3つです。

### 1. 根拠を明文化してから判断する

「なんとなく良さそう」ではなく、「Windows環境からiOSビルドが可能かどうか」という具体的な判断基準に沿って、既存構成(Flutter)と新構成(Expo)を比較する資料を作ってから決めました。思いつきの技術選定変更ではなく、**判断基準を先に固定してから比較する**という順番を守ったのが良かったと思います。

実際に判断材料にした比較表を、当時のドキュメントからそのまま引用します。

| レイヤー | 現行(Flutter) | 変更後(Expo/React Native) |
| --- | --- | --- |
| 言語 | Dart | TypeScript |
| 状態管理 | Riverpod | Zustand または Jotai(軽量・シンプル) |
| ローカルDB | Drift(SQLite) | expo-sqlite(+Drizzle ORM 等)※調査中 |
| チャート | fl_chart(レーダー) | victory-native / react-native-svg 自作 ※レーダー対応を調査中 |
| iOSビルド | 不可(Mac必要) | **EAS Buildクラウド(Windowsから可)** |
| Androidビルド | ローカル | ローカル or EAS Build |
| CI | GitHub Actions(flutter) | GitHub Actions(node)+EAS |
| 課金(将来) | in_app_purchase 等 | **RevenueCat(react-native-purchases)** |
| 分析 | Firebase(v1後半予定だった) | **PostHog(React Native SDK)** |

こうして並べてみると、他の行はどちらでも大差ない中で、「iOSビルド」の行だけが**不可能から可能へ**という質的に違うインパクトを持っていたことが分かります。判断基準を先に決めていたからこそ、この1行の重みに惑わされず、他の変更点(状態管理やチャートライブラリの移行コストなど)も含めて冷静に比較できました。

### 2. 資料は捨てずに転用する

Flutter向けに作っていたセットアップ手順書やDartのスターターコードは、そのまま無駄になったわけではありません。「実装のロジック仕様」としては再利用可能だったので、旧資料は「参考資料」として残し、**ロジックの仕様だけをExpo/TypeScriptへ移植する**方針にしました。ゼロから考え直すのではなく、「何を作りたかったか」の資産は活かす、というのは地味に効くコスト削減です。

思い切ってアーキテクチャを変えられたのは、実際にコードを書き始めるより前のタイミングだったから、というのが大きいと思っています。AIを使う場合でも、実際に手を動かして作り始める前にきちんと考えを整理し、何が本当に必須で、何はそうでないかを見極めておく。それができていれば、方針転換が必要になった時も、最小限の後戻りで目的を達成できるのだと考えています。

### 3. Android版でしっかり作り込む

実際の動作・使い勝手・機能の充足度については、手元でローカルビルドできるAndroid版でひたすら試行錯誤(トライ&エラー)しながら磨き込みました。iOS版のビルドは、納得のいくレベルに達してから初めて行う、という順番を徹底しています。iOSはEAS Buildのクラウドビルドを経由するため、ローカルで完結するAndroidビルドに比べてどうしても1回あたりの確認サイクルが遅くなります。だからこそ、速く回せる方(Android)で作り込みを終わらせてから、遅い方(iOS)は仕上げの確認として最後に回す、という役割分担にしました。

とはいえ、iOS版をビルドしただけで終わらせているわけではありません。実際にiPhone・iPadの実機に入れて、動作確認はきちんと行っています。

## 後日談: 判断は的中した

プロジェクト開始から2週間ほど経った頃、実際にWindows環境からEAS Buildを使ってiOSアプリのビルドに挑戦しました。Apple Developer Programの支払い直後は「有効なチームが紐づいていない」というエラーに遭遇したりもしましたが(これは単にApple側のアカウント有効化待ちの、よくある遅延でした)、最終的には**Windows機だけでiOSアプリのビルド・TestFlightへの配信まで完走**できました。

Macを1台も使わずにAndroid・iOS両方のアプリをビルドできる、という当初の狙い通りの結果になったわけです。

## まとめ

- 技術選定は、プロジェクトの早い段階であれば大胆に見直してよい
- 見直す際は「なぜ変えるか」の判断基準を先に固定する
- 既存の資産(仕様・ドキュメント)は、実装言語が変わっても「考え方」の部分は転用できる
